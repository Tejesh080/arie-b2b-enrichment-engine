# ADR 0005 — Migration source of truth after enabling Supabase GitHub Branching

**Status:** Accepted · **Date:** 2026-08-16

## Context

`migrations/*.sql` plus `scripts/migrate.py` (a hand-rolled runner tracking
applied files by checksum in `public.schema_migrations`) was built and put into
production use in M1 Steps 6 and 7, before Supabase's GitHub integration
(Branching) was enabled on this repository.

Branching provisions an isolated preview database per pull request and applies
schema to it automatically — but only by watching
`supabase/migrations/<timestamp>_<name>.sql`, the Supabase CLI's own
convention, tracked in its own `supabase_migrations.schema_migrations` table.
This repo had neither the directory nor the tracking table Branching looks
for, so enabling it did nothing: preview databases would come up schema-less.

## Decision

`migrations/` remains the single source of truth. It is the only path that
ever touches the **production** database, via `scripts/migrate.py`.

`supabase/migrations/` is a **generated, byte-identical mirror**, produced by
`scripts/sync_supabase_migrations.py` and verified in CI
(`make check-supabase-migrations`). It exists solely so Supabase's GitHub
integration can provision schema on PR preview branches automatically. Nobody
hand-edits a file under `supabase/migrations/`; the sync script derives it
from `migrations/` every time, with synthetic, deterministic timestamps
(`0001` → `20260101000000`, `0002` → `20260101000100`, ...) so regenerating is
always a no-op unless a real migration changed.

`supabase/config.toml` was added minimally (`project_id`, Postgres major
version) — enough for the CLI/Branching to recognize the project, not a full
`supabase init` output. No `supabase/seed.sql`: nothing in this repo currently
writes seed data into Postgres (the eval dataset is generated by
`arie.evalgen` directly into `data/eval/`, not loaded into `eval_leads` by any
pipeline yet), so an empty seed file would document nothing real.

## Rationale

**Why not switch outright to the Supabase CLI convention?** It would mean
losing the checksum guard `scripts/migrate.py` already provides — a migration
edited after it ran anywhere fails loudly rather than silently reapplying or
skipping (see its docstring). That guard predates Branching and stays; nothing
about adopting Branching required removing it.

**Why not leave `supabase/migrations/` empty and let Branching do nothing?**
Then enabling Branching would be inert — preview databases would never
resemble production, defeating the point of turning the feature on.

**Why generate the mirror instead of hand-maintaining two copies?** Two
independently-edited SQL files for the same schema change WILL eventually
drift — someone fixes a bug in one and forgets the other. `make
check-supabase-migrations` in CI makes that structurally impossible: a PR that
adds `migrations/0004_x.sql` without regenerating the mirror fails the build,
not silently ships stale preview schema.

## Consequences

**Positive**

- Preview databases receive the exact same schema as production, generated
  from one file, with an automated check preventing drift.
- Production's safety net (checksum guard, one script, one tracking table) is
  completely unchanged.

**Negative**

- Two directories for what is conceptually one set of migrations. Anyone
  editing schema needs to know `migrations/` is the one to edit and
  `make sync-supabase-migrations` is the one to run afterward — documented
  here and in the sync script's own docstring, not otherwise enforced beyond
  the CI check catching a forgotten regeneration.
- Supabase's own tracking table (`supabase_migrations.schema_migrations`) is
  never written to by `scripts/migrate.py`. If Branching's *production* deploy
  (a separate, opt-in setting in the Supabase dashboard) were ever turned on,
  it would see none of these migrations as applied and would attempt to run
  them fresh. This was verified safe rather than assumed: every statement in
  `migrations/0001-0003` was re-executed directly against the live production
  database, bypassing `scripts/migrate.py` entirely, with zero errors and zero
  side effects (`CREATE TABLE IF NOT EXISTS`, `CREATE OR REPLACE VIEW`,
  `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, `DROP TRIGGER IF EXISTS` +
  `CREATE TRIGGER`, throughout). That property needs to hold for every future
  migration too — write them idempotent, not just once-only-safe.
- Branching's automatic *production* deploy was deliberately left untouched
  (not enabled, not disabled — that toggle lives in the Supabase dashboard,
  outside this repo). Production changes continue exclusively through
  `make db-migrate-prod`
  (`python scripts/migrate.py --target production --apply
  --confirm-production-write`) — three mandatory flags since Productization
  M6, because the runner's older bare invocation had no way to name its
  database and applied unreleased migrations to production once.

## What would change this

If the custom checksum-guard tooling is ever retired in favour of full
Supabase CLI adoption (`supabase db push` etc. as the actual production path),
`migrations/` + `scripts/migrate.py` could be deleted and `supabase/migrations/`
promoted from generated mirror to sole source of truth. Not done here because
nothing about adding Branching support required giving up the existing safety
net.
